# Mehrsprachigkeit (i18n) — Umsetzungsplan

Ziel: Vollständige Übersetzung von Public-Frontend, E-Mails und Reglement auf **EN, FR, HU, CS** (Default: DE). Admin/Display/Audio folgen danach. Neue Sprachen müssen später ohne Code-Änderungen außerhalb der Locale-Dateien ergänzbar sein.

## Architektur-Entscheidungen

| Entscheidung | Begründung |
|---|---|
| `react-i18next` + `i18next` + `i18next-browser-languagedetector` | Plural-Regeln für CS/HU eingebaut, Lazy-Loading, Standard-Ökosystem |
| Locale-Dateien: `frontend/<app>/src/i18n/locales/<lang>.json` | Eine Datei pro Sprache pro App; neue Sprache = neue Datei |
| Zentrale Sprachliste `SUPPORTED_LANGUAGES` in `src/i18n/index.js` | Single Source of Truth; Switcher, Detection und Fallback lesen daraus |
| Sprachwahl: Switcher im Header, Persistenz via `localStorage`, optional `?lang=` URL-Param | SPA ohne Server-Routing; keine SEO-Pfade nötig (öffentliche Inhalte sind primär Live-Daten) |
| Fallback-Sprache: `de` | Alle Inhalte existieren garantiert auf Deutsch |
| Backend liefert strukturierte Daten statt fertiger Strings | `'Finale'`/`'KO-Runde'` aus `services/tournaments/` werden zu `{ type, round, ... }`; Frontend übersetzt |
| API-Fehler als Codes (`TEAM_NOT_FOUND`) statt deutscher Texte | Frontend mappt Code → übersetzte Meldung; Backend bleibt sprachneutral |
| E-Mail-Sprache = Feld `language` in `tournament_registrations` | Empfängersprache muss persistiert sein; Default aus Browser-Locale, im Formular änderbar |
| `<html lang>` dynamisch via i18n setzen | Accessibility + korrekte Screenreader-Aussprache |

## Neue Sprache hinzufügen (Zielbild)

1. `frontend/public/src/i18n/locales/<lang>.json` anlegen (Kopie von `de.json`, übersetzen)
2. Sprachcode in `SUPPORTED_LANGUAGES` eintragen
3. `backend/src/services/mail/templates/<lang>/` anlegen
4. Reglement-Variante + PDF bereitstellen
5. Fertig — Detection, Switcher, Fallback greifen automatisch

## Phase 1 — Fundament (Public-App) ✅ UMGESETZT

- [ ] Dependencies: `react-i18next`, `i18next`, `i18next-browser-languagedetector` in `frontend/public` (gepinnt, >7 Tage alt)
- [ ] `src/i18n/index.js`: Init, `SUPPORTED_LANGUAGES = ['de','en','fr','hu','cs']`, Fallback `de`, Detection-Reihenfolge `querystring → localStorage → navigator`
- [ ] `de.json` aus allen vorhandenen Texten extrahieren (~75 Stellen): `App.jsx`, `components/**`, `constants/tabs.js` (Tab-Labels als Keys), `context/PublicAppContext.jsx`
- [ ] Komponenten auf `useTranslation()`/`t('key')` umstellen
- [ ] `useLocale()`-Helper: ersetzt alle hardcodierten `'de-DE'` in `toLocaleDateString`/`Intl.DateTimeFormat` (5 Stellen in public)
- [ ] `<html lang>` per Effekt auf `i18n.language` setzen
- [ ] `LanguageSwitcher`-Komponente in `PublicHeader` (Sprachcodes, keine Flaggen)
- [ ] Abnahme: `en.json`/`fr.json`/`hu.json`/`cs.json` vollständig; Key-Coverage-Skript (alle Sprachen haben alle Keys) als `npm run i18n:check`

## Phase 2 — Backend: sprachneutrale API ✅ UMGESETZT

- [ ] `services/tournaments/helpers.js`: Label-Generierung (`'Finale'`, `'KO-Runde'`, `'Platzierungsrunde X-Y'`) → strukturierte Objekte `{ stageType, round, participantCount }`
- [ ] `services/tournaments/summary.js`: `'Gesamtbilanz'` etc. → Codes
- [ ] Frontends (public, display, admin) mappen Codes via `t()` auf übersetzte Labels
- [ ] Routes: `message: '...'` → `{ code: 'TEAM_NOT_FOUND' }` (156 Stellen in `routes/*.js`); Frontends zeigen `t('error.TEAM_NOT_FOUND')` mit Fallback auf `message` (Abwärtskompatibilität während Übergang)
- [ ] Abnahme: kein deutscher String mehr in API-Payloads (Grep auf `ä|ö|ü|ß` in `backend/src/routes` + `services/tournaments` = 0 Treffer in Response-Strings)

## Phase 5 — Display, Audio, Admin ✅ UMGESETZT

- [ ] Display (~30 Texte): gleiche i18n-Struktur; Sprache via URL-Param `?lang=` (Beamer ohne Interaktion) + Default `de`
- [ ] Audio (~5 Texte): minimal, Deutsch reicht ggf. — Entscheidung offen
- [ ] Admin (~100 Texte): gleiche Struktur; intern, daher niedrigste Priorität
- [ ] Backend-Seeds in `db/schema.js` (Audio-Cue-Beschreibungen auf Deutsch): auf `de` belassen, im Admin als solche kennzeichnen

## Was sonst noch wichtig ist

| Thema | Maßnahme |
|---|---|
| Lange Wörter (HU/CS brechen Layouts) | Playwright-Overflow-Audit (390px/768px) pro Sprache in alle Tabs — Skript aus Session 2026-08-23 wiederverwenden |
| Pluralformen | i18next-Pluralregeln nutzen; keine String-Konkatenation wie `count + ' Spiele'` — immer `t('games', { count })` |
| Grammatik statt Konkatenation | Keine Satzbausteine (`'Spiel um' + x`); ganze Sätze pro Key |
| Datums-/Zahlenformate | `Intl` mit aktiver Locale; nie hardcodiert `de-DE` |
| Nutzergenerierte Inhalte | Turniernamen, Teamnamen, Beschreibungen bleiben einsprachig (Admin-Eingabe) — bewusste Grenze, nicht übersetzen |
| Übersetzungs-Workflow | `npm run i18n:check` in CI: fehlende Keys pro Sprache = Build-Fehler |
| Analytics | Plausible-Events um `language`-Dimension ergänzen (optional) |

## Reihenfolge-Empfehlung

Phase 1 → 4 → 3 → 2 → 5, falls Publikumswirkung priorisiert wird (Reglement vor E-Mail). Technisch sauberer: 1 → 2 → 3 → 4 → 5 (Backend zuerst sprachneutral machen).
